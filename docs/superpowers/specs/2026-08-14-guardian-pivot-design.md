# GuArDian 피벗 설계 — 광고 표시에서 디지털 피해 예방으로

- 작성일: 2026-08-14
- 상태: 진행 중 (Phase 4a 구현과 함께 작성)
- 브랜치: `phase4-guardian-pivot` (베이스: `phase3-scroll-follow-merge`)

## 배경

피드백과 자료조사를 거쳐 프로젝트를 재정의했다. 요지는 다음과 같다.

> 광고 자체가 불편하다는 문제를 넘어, **광고와 연결 링크가 디지털 피해의 진입점**이
> 될 수 있으며 고령층은 이를 사전에 구분하고 대응하기 어렵다.

GuArDian은 광고를 일괄 제거하는 앱이 아니다. 광고임을 명확히 표시하고, 광고
링크로 발생할 수 있는 사기성 쇼핑몰·피싱·악성 앱 설치·원치 않는 결제 위험을
**사전에 이해하고 피하도록 돕는 디지털 안전 서비스**다.

이 문서는 재정의된 기획(전체 내용은 팀 노션 참고)을 기존 코드베이스 위에
어떻게 얹을지를 다룬다. 기획 요약이 아니라 **코드 관점의 이행 계획**이다.

## 1. 판단 체계의 변화

기존에는 "광고인가?"라는 단일 질문에 답했다. 이제는 두 질문을 분리한다.

1. 현재 화면이 광고인가 — **기존 3-Layer가 이미 하는 일**
2. 광고 화면 또는 연결 링크가 사용자에게 위험한가 — **신규**

### 1.1 위험도 분류

| 위험도 | 판단 기준 예시 | 사용자 대응 |
|---|---|---|
| **저위험** | 광고임이 명확, 광고주·연결 주소 일치, 위험 신호 없음 | 파란 테두리 + `광고` 표시 후 허용 |
| **중위험** | 광고·콘텐츠 구분 곤란, 과도한 할인, 낯선 도메인, 반복 리다이렉트 | 노란 테두리 + 판단 이유 표시, 이동 전 확인 |
| **고위험** | 알려진 악성 도메인, 브랜드-주소 불일치, 외부 APK, 개인정보·결제 요구 | 광고와 링크 자동 차단, `계속 진행` 없음 |
| **추가 확인 필요** | 목적 URL 미확보 또는 분석 불충분 | 분석 한계와 복귀 권고 표시 |

**`추가 확인 필요`는 위험 등급이 아니라 분석 상태다.** 분석하지 못한 화면을
저위험으로 처리하지 않는다. 코드에서는 `RiskLevel` enum(LOW/MEDIUM/HIGH)과
별개로 `RiskAssessment` sealed class의 `Unverified` 상태로 모델링해, 등급이
없는 채로 "안전"으로 흘러가는 경로를 타입 수준에서 막는다.

### 1.2 보호 수준

| 보호 수준 | 저위험 | 중위험 | 고위험 |
|---|---|---|---|
| **안내형** | 표시 후 허용 | 이유 표시 + 사용자 선택 | 자동 차단 |
| **균형형** (기본) | 표시 후 허용 | 안내형 + 투터치 | 자동 차단 |
| **강력 보호형** | 표시 후 허용 | 기본 차단 | 자동 차단 |

이 매트릭스는 `RiskPolicy` 순수 함수로 구현한다(Phase 4a). 고위험은 보호
수준과 무관하게 항상 차단이고 우회 경로가 없다 — 이 속성은 단위 테스트로
고정한다.

## 2. 기존 코드 → 새 아키텍처 매핑

기존 코드의 대부분이 새 기획의 부품으로 그대로 쓰인다. 버릴 것은 거의 없다.

| 기존 | 새 역할 | 변경 |
|---|---|---|
| `AdGuardAccessibilityService` + 스크롤 정지 예측 | 화면 감지 진입점 (유지) | 위험도 표시 분기 추가 |
| `region/` Layer 1 (라벨 감지) | 광고 탐지 1차 경로 | 유지. 로직·상수 변경 금지 원칙 그대로 |
| `agent/` Layer 2 파이프라인 | 광고 탐지 2차 경로 + 위험 분석 입력 수집 | `AdClassifier` 구현체를 온디바이스로 교체 |
| `GeminiClassifier` | **폐기 예정** — 새 원칙은 외부 LLM API 미사용 | 온디바이스 구현 완성 전까지 개발 검증용으로만 유지 |
| `guard/` Layer 3 (설치 유도 차단) | 고위험 대응의 일부 (APK·스토어 유도) | 위험도 체계에 편입 |
| `overlay/AdBorderOverlay` | 위험도별 테두리 (파랑/노랑/빨강 + 텍스트 배지) | 색·배지 확장. `FLAG_NOT_TOUCHABLE` 원칙은 저·중위험에 유지 |
| Room `ad_verdict` | 광고 여부 캐시 (유지) | `url_verdict` 테이블 추가 (v3) |
| `detector/` 블랙리스트 (보류였음) | **부활** — 고위험 "알려진 악성 도메인" 판정 | 광고 도메인 목록 대신 악성 도메인 목록로 용도 변경 검토 |
| `FirebaseRepo` (연결 코드 방식) | 가족 계정 + 프로필 방식으로 개편 | 큰 변경. Phase 4f |
| `GuardianActivity` | 보호자 대시보드 (위험 유형·차단 횟수·리포트) | 확장 |
| `logger/AdEventLogger` | 고위험 차단 이벤트만 전송 (최소 정보 원칙 강화) | 이벤트 스키마에 위험등급·유형 추가 |

### 이름에 대해

앱 이름은 GuArDian으로 바꾼다(`strings.xml`). **패키지명 `com.senioradguard`는
당분간 유지한다** — Firebase 프로젝트가 패키지명에 묶여 있어 바꾸면 팀원 전원의
`google-services.json` 재발급이 필요하다. 스토어 제출 전에 한 번에 바꾼다.

## 3. 신규 컴포넌트

### 3.1 위험도 도메인 (`risk/`) — Phase 4a, 이번 구현

```
risk/
├── RiskLevel.kt        LOW/MEDIUM/HIGH + 사용자 표시 어휘(광고/주의/위험)
├── RiskAssessment.kt   Assessed(level, reason) | Unverified(limitation)
├── ProtectionLevel.kt  GUIDE/BALANCED/STRICT (기본 BALANCED)
├── RiskPolicy.kt       (보호수준 × 평가) → UserAction 매트릭스, 순수 함수
└── UrlNormalizer.kt    캐시 키용 URL 정규화, 순수 함수
```

전부 Android 의존이 없는 순수 Kotlin이라 JVM 단위 테스트 대상이다.

### 3.2 URL 판정 캐시 (`detector/db/UrlVerdict`) — Phase 4a, 이번 구현

한 번 분석한 URL은 저장하고 같은 URL이 다시 나타나면 즉시 적용한다.

```
광고 탐지
   ↓
Room에서 URL 판정 확인
   ├─ 유효한 결과 있음 → 즉시 위험도 표시
   └─ 없음·만료 → URL 정보 수집 → 온디바이스 분석 → 저장 → 표시
```

저장 항목: 정규화 URL(PK), 위험 등급, 판단 이유, 최종 도착 URL, 분석 시각,
유효기간. **`Unverified`는 저장하지 않는다** — 분석 실패를 캐시하면 다음
기회에 분석할 수 있는 URL이 영영 미분석으로 남는다.

`ad_verdict`와 별도 테이블인 이유: `ad_verdict`는 "이 카드가 광고인가"(화면
텍스트 기준), `url_verdict`는 "이 링크가 위험한가"(목적지 기준)로 키도 수명도
다르다. 광고 판정은 30일 TTL이지만 위험 판정은 피싱 사이트의 수명이 짧아
더 짧은 유효기간이 필요할 수 있다 — 그래서 행마다 `validUntil`을 둔다.

### 3.3 URL 확보·분석 모듈 (`analysis/`) — Phase 4b

**가장 어려운 부분이고, 정직하게 한계를 적어둔다.**

접근성 트리는 광고의 목적 URL을 거의 노출하지 않는다. 웹 배너의 href는
접근성 노드에 실리지 않고, 네이티브 광고 SDK는 클릭 시점에야 URL을 만든다.
확보 경로는 세 가지다.

1. **사전 확보 (드묾)**: 노드 텍스트·contentDescription에 URL이 보이는 경우
2. **사후 개입 (주 경로)**: 클릭 → 브라우저 전환 감지(`TYPE_WINDOW_STATE_CHANGED`)
   → 주소창 노드(`url_bar`)에서 도착 URL 확보 → 캐시 조회 → 고위험이면
   즉시 `GLOBAL_ACTION_BACK` + 차단 안내. "페이지를 보기 전에 막는다"가 아니라
   "페이지에서 즉시 빼낸다"에 가깝다
3. **격리 분석**: 확보한 URL을 사용자 브라우저와 분리된 분석 환경(앱 내
   HttpURLConnection, 쿠키·JS 미실행)에서 리다이렉트 체인·최종 도메인·페이지
   신호(APK 링크, 결제·개인정보 폼)를 수집

목적 URL을 끝내 못 얻으면 `Unverified`로 표시한다. 검증 지표의 "목적 URL
확보율"이 이 모듈의 성적표다.

분석 과정에서 파일 다운로드, 외부 앱 실행, 결제·개인정보 입력을 절대
수행하지 않는다.

### 3.4 온디바이스 LLM (`AdClassifier` 구현체 교체) — Phase 4c

새 원칙: 자체 서버·외부 LLM API를 쓰지 않고 어르신 기기에서 분석한다.
`AdClassifier` 인터페이스가 처음부터 교체점으로 설계되어 있어 파이프라인은
손대지 않는다.

후보와 트레이드오프:

| 후보 | 장점 | 위험 |
|---|---|---|
| Gemini Nano (AICore) | 시스템 관리, 배터리 효율 | **지원 기기가 플래그십 위주** — 어르신 폰에서 대부분 불가 |
| MediaPipe LLM Inference + Gemma 1B급 | 기기 제약 적음, 오프라인 | 모델 ~0.5–1GB 다운로드, 중급기 추론 속도 미검증 |
| llama.cpp JNI | 제어권 최대 | 유지보수 부담 최대 |

**열린 위험**: 어르신이 실제로 쓰는 중저가·구형 기기에서 1B급 모델의 추론
지연·발열·배터리를 감당할 수 있는지 검증된 바 없다. Phase 4c 첫 작업은 구현이
아니라 **대상 기기에서의 성능 실측**이어야 한다. 실측이 실패하면 "온디바이스
규칙·블랙리스트 + LLM은 상위 기기만" 같은 단계적 적용으로 물러선다.

### 3.5 OCR 폴백 — Phase 4d

접근성 노드에서 광고 표시를 못 찾으면 ML Kit 온디바이스 텍스트 인식으로
이미지 안의 문구를 추출해 재확인한다. 이전 설계에서 제거했던 OCR의 재도입인데,
이번에는 클라우드가 아니라 **온디바이스 ML Kit**이고 화면 캡처는 이미 검증된
`AccessibilityService.takeScreenshot()`(API 30+)을 쓴다.

### 3.6 가족 계정 (`FirebaseRepo` 개편) — Phase 4f

연결 코드 방식(ANDROID_ID)을 버리고 **하나의 가족 계정 + 보호자·어르신
프로필** 구조로 바꾼다. 기존 "보호자 연결 승인 부재" 문제가 이 개편으로
자연히 해소된다 — 같은 계정으로 로그인해야 하므로 코드 유출로 남이 구독하는
경로가 사라진다.

- 익명 인증 → 이메일/소셜 로그인 (어르신 기기는 가족이 최초 1회 설정)
- 보호자 모드 진입에 PIN 또는 생체인증
- 어르신 프로필 생성 시 공유 정보·보호자 권한 고지 + 동의, 동의 철회 기능
- 고위험 차단 시 위험 등급·유형·차단 여부·발생 시각·앱 정보**만** 전송
  (전체 화면·페이지 내용 전송 금지 — 기존 최소 정보 원칙 유지·강화)
- FCM으로 보호자 실시간 알림, 주간·월간 리포트

## 4. 로드맵

| Phase | 내용 | 상태 |
|---|---|---|
| **4a** | 위험도 도메인 모델 + 정책 매트릭스 + URL 판정 캐시 + 테스트 | **이번 구현** |
| 4b | URL 확보(사후 개입 포함)·격리 분석 모듈, 신호 기반 위험도 산정 | |
| 4c | 온디바이스 LLM — 대상 기기 성능 실측 먼저, 그다음 `AdClassifier` 교체 | |
| 4d | OCR 폴백 (ML Kit 온디바이스) | |
| 4e | 오버레이 위험도 색상·배지, 중위험 투터치, 고위험 차단 + 안전 복귀, 보호 수준 설정 UI | |
| 4f | 가족 계정·프로필, PIN, FCM 알림, 보호자 대시보드 확장, 리포트 | |

순서 근거: 4a가 공통 어휘(위험도·정책)를 고정해야 나머지가 같은 타입 위에서
움직인다. 4b·4c는 병렬 가능하다(4b는 신호 수집, 4c는 판단기). 4e는 4a의
타입만 있으면 시작할 수 있어 UI 담당이 4b·4c와 병렬로 진행 가능하다.

## 5. 정책·심사 리스크 (기존 원칙과의 충돌 지점)

기존 README의 대원칙은 "광고 클릭·구매·설치를 방해하면 구글 정책 위반"이었고
Layer 1·2 오버레이는 `FLAG_NOT_TOUCHABLE`을 강제했다. 새 기획은 고위험 광고를
**차단**하고 중위험을 **간섭**한다. 정리하면:

- **저위험**: 기존과 동일 — 표시만, 터치 통과. 문제 없음
- **고위험**: 성격이 Layer 3과 같다 — 광고 방해가 아니라 **사기·악성 행위
  직전 개입**. 접근성 서비스의 본래 목적(사용자 보호)으로 심사 소명 가능
- **중위험이 회색지대다.** 확정적이지 않은 판정으로 터치를 가로채는 것이라,
  투터치 확인은 "차단"이 아니라 "확인"으로 설계하고(진행 경로를 항상 남김),
  강력 보호형의 기본 차단은 **사용자가 명시적으로 선택한 설정**이라는 점을
  UI와 스토어 심사 자료에 남긴다

접근성 권한·`SYSTEM_ALERT_WINDOW` 사용 목적 명시는 기존 배포 전 체크리스트
그대로 유효하다.

   - `RiskPolicyTest` — 매트릭스 전수(3×3) + 불변 속성 2개
     (고위험은 어떤 보호 수준에서도 차단, `Unverified`는 절대 허용 표시가 아님)
   - `UrlNormalizerTest` — 추적 파라미터 제거, 대소문자, 기본 포트,
     프래그먼트, 파라미터 정렬, 비URL 입력
   - `UrlVerdictDaoTest`(계측) — CRUD, 유효기간, 만료 정리
4. `app_name` → GuArDian, README 상단에 방향 전환 안내

**이 커밋은 아직 아무 동작도 바꾸지 않는다.** 새 타입과 캐시는 존재하지만
서비스가 아직 참조하지 않는다. 의도적이다 — 어휘를 먼저 합의하고(이 문서 +
테스트가 명세), 동작 변경은 4b·4e에서 별도 커밋으로 나눈다.

## 7. 검증 계획과의 연결

기술 지표 중 이번 증분과 직접 닿는 것:

- **위험도 분류 정확도** → `RiskPolicy`가 분류와 대응을 분리해두었으므로,
  분류기(4b·4c)를 바꿔도 대응 정책 테스트는 그대로 유효
- **목적 URL 확보율** → 4b에서 `Unverified` 비율로 측정 가능해짐
- **신규 URL 최초 분석 시간** → `url_verdict.analyzedAt`으로 측정 기반 마련
