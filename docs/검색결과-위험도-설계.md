# 검색 결과 위험도 (serp) — 설계와 검증

- 작성일: 2026-08-14
- 패키지: `com.guradian.serp`
- 담당 역할: 역할 분담 **2번** — "구글·크롬 검색 결과에서 사이트마다 위험도 상·중·하"
- 광고 감지(역할 1)·탈출(역할 3)과 **코드가 겹치지 않는다.** 별도 패키지, 별도 오버레이 창.

---

## 1. 무엇이 바뀌었나 — 비전 → 텍스트

senioradguard V3는 검색 결과도 **스크린샷을 찍어 비전 모델**에 넘겼다
(`vision/SearchResultScanner` → `VisionRiskPipeline.classify`). 광고 배너와 같은 경로를 썼기 때문이다.

배너에는 그럴 이유가 있다. 배너는 그림 한 장이라 무엇을 파는지 알려면 픽셀을 봐야 한다.
**검색 결과는 다르다.** 도메인·제목·설명이 전부 접근성 트리에 글자로 들어 있다.

그래서 이 구현은 그림을 아예 만들지 않는다. 사라지는 것:

| 비전 경로에서 필요했던 것 | 텍스트 경로 |
|---|---|
| 스크린샷 권한 · `takeScreenshot` 호출 간격 제한 | 없음 |
| 비트맵 복사 → 영역별 크롭 → 그레이스케일 → JPEG 인코딩 | 없음 |
| dHash 지문 · 이웃 지문 비교 (같은 배너 재판별 방지) | 호스트 문자열이 곧 캐시 키 |
| 이미지 토큰 (장당 수백~수천) | 텍스트 1.2k 토큰 / 화면 |
| "화면 그림이 통째로 나간다"는 프라이버시 부담 | 검색 결과에 이미 공개된 제목·도메인만 |

남은 것은 **접근성 노드 순회 + 문자열 규칙 + 텍스트 판별 1회**뿐이다.

## 2. AI가 분석하는 트리거 — 네 개의 관문

판별기(Gemini)는 아래 네 관문을 **모두** 통과했을 때만 호출된다.

```
① 화면 관문   지금 검색 결과 화면인가?
             · 크롬  → 주소가 google.com/search · search.naver.com · search.daum.net …
             · 구글 앱 → **주소창이 없다.** 검색어 칸(googleapp_srp_search_box_text)에
                        글자가 있는지로 판단한다. 홈 피드에도 큰 카드가 잔뜩 있어서
                        패키지명만으로 통과시키면 피드를 계속 훑게 된다
             → 아니면 트리를 훑지도 않는다. 뉴스를 읽는 동안 이 기능은 잠들어 있다
                                                        (SerpScanner.isSearchScreen)
        ↓
② 유휴 관문   화면 변경이 멈추고 700ms 지났는가?
             스크롤 중에는 위치만 따라가고 판별기는 부르지 않는다
                                                        (SerpTracker.IDLE_MS)
        ↓
③ 변경 관문   이번 화면의 호스트 구성이 직전과 다른가?
             같은 화면이면 캐시된 판정을 그대로 쓴다
                                                        (SerpRiskEngine.signatureOf)
        ↓
④ 미지 관문   규칙으로도 캐시로도 결론이 안 난 결과가 있는가?
             ├ 규칙이 '위험'(70+) 확정  → AI 안 부름 (누누티비·도박·성인)
             ├ 알려진 도메인 + 위험 신호 0 → AI 안 부름 (티빙·넷플릭스·KBS)
             ├ 캐시에 있음 (호스트 단위, 7일) → AI 안 부름
             └ 나머지 = 처음 보는 도메인    → **여기 남은 것만**
                                                        (SerpRules.resolve · 캐시)
        ↓
   배치 1회 호출 — 화면당 1번. 항목이 2개든 8개든 호출 수는 같다
```

추가 안전장치: 화면당 최대 8건(`MAX_BATCH`), 시간당 30회 토큰버킷, 429 응답 시 5분 쿨다운.

### 왜 버튼을 누를 때가 아닌가

광고 판별(Layer 2)은 `[광고 찾기]`를 눌러야 돈다. 검색 결과는 그럴 수 없다 —
위험도는 **누르기 전에** 보여야 의미가 있고, 검색할 때마다 버튼을 한 번 더 누르게
하면 어르신은 그냥 안 누른다. 대신 나가는 정보를 줄였다: 화면 그림도 페이지 본문도
아니고, 검색 결과에 이미 공개돼 있는 **제목 · 설명 · 도메인**만 나간다.

## 2-1. 스크롤을 어떻게 따라가는가 — 판정과 좌표의 분리

**이 절이 이 기능에서 가장 중요한 설계다.** 실기기에서 드러난 두 결함이 여기서
나왔고, 둘 다 같은 원인이었다.

처음 구현은 `evaluate()`가 "이 사각형에 이 판정"을 함께 돌려줬다. 판정과 좌표가
한 덩어리라 **화면이 움직이면 판정까지 같이 못 쓰게 됐다.**

- 스크롤하면 배지가 사라짐 → 좌표가 낡았다는 이유로 판정을 통째로 버림
- 판별기 응답이 100% 버려짐 → 돌아왔을 때 좌표가 이미 달라져 있음

둘을 갈랐다.

```
  판정 = 호스트에 붙는다 (tvhot2.com → 위험)    SerpRiskEngine.known()  — 화면과 무관
  좌표 = 화면에서 매번 새로 읽는다               SerpTracker.anchors
  그리기 = anchors를 돌며 호스트로 판정을 조회    SerpTracker.redraw()
```

이렇게 하면 두 결함이 **고쳐지는 게 아니라 존재할 수 없게 된다.**
스크롤하면 좌표만 새로 읽어 다시 그리고(판정은 그대로 있다), 판별기 응답이 5초 뒤에
와도 호스트에 얹으면 그 시점 좌표에 저절로 붙는다. **화면 세대(generation) 비교 자체가
사라졌다** — 늦게 온 응답을 버릴 이유가 없어졌기 때문이다.

`SerpTracker`는 두 속도로 돈다.

| | 주기 | 하는 일 | 판별기 |
|---|---|---|---|
| 위치 갱신 | 이벤트마다 (150ms 스로틀) | 트리에서 좌표만 다시 읽어 그린다 | 안 부름 |
| 판정 갱신 | 화면이 700ms 조용해진 뒤 | 규칙 · 캐시 · 배치 판별 | 여기서만 |

곁들인 장치 세 가지 — 전부 `BorderTracker`가 광고 테두리에서 쓰던 것과 같다.

- **요청을 버리지 않는다.** 스로틀 구간이나 스캔 진행 중에 온 요청은 트레일링으로
  미룬다. 버리면 드래그의 마지막 위치를 잃어 손 뗀 자리에서 배지가 어긋난 채 멈춘다
- **되밀기 보정.** 스캔이 도는 동안 더 구른 만큼(`scrollSinceScanStart`) 결과를 되민다.
  안 하면 배지가 뒤로 튄다
- **빈 화면 히스테리시스.** 결과를 못 찾은 스캔이 3번 연속돼야 지운다. 한 번에 지우면
  지연 로딩·예산 절단 때마다 배지가 깜빡이고, 정작 위험한 결과 위에서 경고가 사라진다

## 3. 위험도 상·중·하 — 점수 만드는 법

V3(`url/UrlSignals` · `url/RiskAggregator`)에서 검증된 식을 그대로 옮겼다.
축은 넷에서 셋으로 줄였다 — 광고 트래킹 축은 검색 결과에 나타나지 않는다.

```
점수 = 가장 강한 신호 + (나머지 신호 합 ÷ 3) + 신뢰 가산(음수)
등급 = 확인 안 됨(표시 없음) / 0~39 하(안전·초록) / 40~69 중(주의·주황) / 70~100 상(위험·빨강)
```

### 네 번째 등급 — '확인 안 됨'

**"걸린 규칙이 없다"는 '안전'이 아니다.** 우리 목록은 작고 앞으로도 완결되지 않는데,
0점을 초록으로 옮기면 **모르는 사이트 전부에 안전 도장을 찍게 된다.** 어르신이 그
초록을 믿고 누르는 순간, 그 초록에는 아무 근거도 없었던 것이 된다.

그래서 초록은 근거가 있을 때만 붙는다 — 알려진 곳 목록에 있거나, 판별기가 실제로
보고 안전하다고 했을 때. 그 외에는 **아무것도 그리지 않는다**(`RiskGrade.UNKNOWN`).
판별기를 못 부르는 상황(키 없음·상한 초과·오프라인)에서 이 구분이 특히 중요하다.

다만 침묵과 무시는 다르다. 위험 신호가 하나라도 잡혔으면 판별기가 없어도 경고는
그대로 남는다 (`RiskAggregator.ruleVerdict`).

전부 더하지 않는 이유: 더하면 사소한 신호 다섯 개가 확정 신호 하나를 이겨버리고,
규칙을 하나 추가할 때마다 기존 판정이 통째로 흔들린다.

**확정 신호(hard)는 하한이 된다.** 판별기가 "안전하다"고 답해도 그 아래로는 안 내려간다.
신뢰 가산은 하한에 반영하지 않는다 — 네이버 카페라는 사실이 그 글이 도박을 권한다는
사실을 지워주지 않기 때문이다.

### 규칙과 판별기의 역할 분담

- **판별기가 최종 판단**을 하고, 규칙은 하한만 받친다.
  순서를 뒤집으면(규칙이 판단, AI가 보정) 목록에 없는 새 사이트를 영영 못 잡는다.
- 다만 **규칙이 '위험'으로 확정한 것은 판별기를 거치지 않는다.**
  확정하면 고칠 기회가 없으므로 경계를 70에 뒀다 (§4 참고).

## 4. 검증

### 4-1. 실제 Gemini API 표본 (2026-08-14, gemini-3.1-flash-lite)

| 표본 | 건수 | 결과 |
|---|---|---|
| 정상 OTT·방송·포털 + 불법 다시보기 | 12 | 12/12 |
| 덜 알려진 정상 서비스 · 사칭 · 도박 · 성인 · APK · IP직결 · 단축주소 | 15 | 14/15 · **오탐 0 · 미탐 0** |
| 실제 운영 형태(규칙 신호 동봉, 판별기가 실제로 보는 것만) | 10 | 9/10 · **오탐 0 · 미탐 0** |

불일치 1건은 `blog.tistory.com`의 "무료 다시보기 사이트 순위 TOP10" 글이다.
사람 기준으로는 '중'(플랫폼은 정상), 모델은 '상'(내용이 불법 사이트 안내). 모델 쪽이
어르신 보호 관점에서 더 맞는 답으로 보인다.

**비용:** 화면당 배치 1회 · 입력 1.2~1.4k 토큰 · 응답 5~9초 · finishReason=STOP.

### 4-2. 경계값을 70으로 올린 이유 (표본으로 결정)

| 규칙 확정 경계 | 규칙이 끝내는 비율 | 규칙의 오답 |
|---|---|---|
| 40 ('주의' 이상) | 25/27 | **2건** — APK 배포 사이트와 IP 직결 사이트를 '중'으로 확정 (판별기는 90점대 '상') |
| **70 ('위험' 이상)** | 20/27 | **0건** |

호출 비용은 거의 그대로다 — 판별기 호출은 항목당이 아니라 **화면당 1회**라서,
한 화면에서 판별기로 내려가는 항목이 2개든 12개든 호출 수는 같다.

### 4-4. 실기기 검증 (2026-08-14, SM-S937N, 크롬, 구글 "드라마 다시보기")

실제 검색 상위에 불법 사이트가 그대로 떠서 표본을 따로 만들 필요가 없었다.

| 결과 | 판정 | 누가 판정했나 |
|---|---|---|
| `tvhot2.com` (티비핫) | 상 · 빨강 | **규칙** — 이름만으로 확정, 호출 0 |
| `nooo16.tv` (누누티비) | 상 · 빨강 | **AI** — 규칙 목록엔 `noonoo`만 있고 `nooo16`은 없다 |
| `noonootvk2.store` | 상 · 빨강 | **규칙** |
| `homepy.korean.net` ("주소월드 바로가기") | 상 · 빨강 | **AI** — 도메인은 멀쩡한데 설명이 불법 사이트 모음 |
| `vod.kbs.co.kr` · `imbc.com` | 하 · 초록 | **규칙** — 호출 0 |

```
serp 검색어='드라마 다시보기' 결과=3 판별=1 생략=false {상=2, 하=1}   ← 첫 화면: 3건 중 AI 1회
serp 검색어='드라마 다시보기' 결과=5 판별=2 생략=false {하=3, 상=2}   ← 스크롤 후
serp 검색어='드라마 다시보기' 결과=3 판별=0 생략=false {상=2, 하=1}   ← 재방문: 캐시 적중, AI 0회
```

확인된 것: 결과 추출 · 도메인 줄 읽기 · 규칙/AI 분담 · 배지 렌더링 · 스크롤 추종 ·
검색 화면 이탈 시 배지 제거 · 캐시 적중 · **광고 감지(task 1) 오버레이와 공존**
(같은 화면에서 두 창이 서로를 지우지 않는다).

#### 실기기에서만 드러난 결함 세 개 — 전부 수정됨

1. **배지가 결과 제목을 덮었다.** 위(TOP)에 붙였더니 어르신이 읽어야 할 제목을 정확히
   가렸다. 아래(BOTTOM)로 옮기고 가로 한 줄로 눕혔다 — 가려지는 것은 설명 마지막 줄이다.
2. **스크롤하면 배지가 전부 사라졌다.** 크롬이 주소창을 접어 트리에서 없애므로
   ① 관문이 false가 됐다. 화면엔 누누티비 클론이 떠 있는데 경고가 하나도 없었고,
   **스크롤해서 내려가는 결과가 정확히 어르신이 덜 살펴보는 결과다.**
   `BrowserHost`와 같은 방식으로 마지막 주소를 기억해 메웠다 (`SerpScanner.resolvePageUrl`).
3. **판정이 100% 버려졌다.** 이벤트가 올 때마다 화면 세대를 올렸는데, 구글 검색 화면은
   가만히 둬도 `CONTENT_CHANGED`를 계속 보낸다. 판별기 왕복(2~5초) 사이에 세대가 반드시
   바뀌어 스캔 로그는 정상인데 배지만 안 떴다. 세대를 올리는 것은 **스크롤과 화면 이동뿐**
   으로 바꿨고, 버릴 때 로그를 남기게 했다. 진행 중이라 요청이 버려지던 것도 재예약으로 고쳤다.

## 5. 파일

```
serp/
  SerpRisk.kt             등급(확인안됨·하·중·상) · 분류 · 판정
  SerpResult.kt           결과 한 칸(좌표 없음) · 호스트 분해(UrlParts)
  KnownSites.kt           ★ 사이트 이름 목록 — 원격 피드로 갈아끼우는 자리
  UrlSignals.kt           세 축의 규칙 신호 — 네트워크 안 씀
  RiskAggregator.kt       점수 합성 · 확정 신호 하한 · '확인 안 됨' 판단
  SerpRules.kt            ★ AI를 부를지 정하는 문지기
  SerpClassifier.kt       판별기 인터페이스(배치) + 규칙 전용 대역
  GeminiSerpClassifier.kt 텍스트 배치 판별 — 화면당 1회
  SerpRiskEngine.kt       ★ 호스트별 판정 저장소 · 트리거 · 캐시 · 상한
  SerpTracker.kt          ★ 스크롤 추종 — 좌표를 매번 새로 읽어 판정을 얹는다
  SerpScanner.kt          접근성 노드 → 결과 카드 (스크린샷 없음)
  SerpBadgeOverlay.kt     배지 (별도 창 · FLAG_NOT_TOUCHABLE)
```

서비스 연결은 `GuardianAccessibilityService`의 `// ── region: serp ──` 안에 있고,
공유 구간에 넣은 것은 세 줄뿐이다: dispatch의 `serpTracker.onScroll/onEvent` 두 줄,
`onDestroy()`의 `serpTracker.clear()` 한 줄.

## 6. 배포 전에 반드시 할 것

- `GeminiSerpClassifier`는 앱에서 Gemini를 직접 부른다. **APK를 뜯으면 키가 그대로 나온다.**
  `SerpClassifier` 인터페이스가 교체점이고, 서버 경유 구현으로 갈아끼우면
  파이프라인·캐시·배지는 손대지 않는다.
- 사이트 이름 목록은 [KnownSites]로 빼두었다. 방송통신심의위원회 차단 목록이나 KISA
  피드를 받으면 **그 인터페이스 구현 하나만 갈아끼우면 된다** — `UrlSignals`도
  `SerpRules`도 손대지 않는다. `BuiltInKnownSites + FeedSites`처럼 더하면 씨앗을
  지우지 않고 얹을 수 있어, 피드를 못 받아도 최소한 씨앗만큼은 계속 동작한다.
